# Validation de CaissePro — 5 novembre 2026

## Adaptation monocaisse et multicaisse — validation courante

**119 tests automatisés exécutés et réussis pour cette adaptation**, plus une nouvelle compilation Tauri Linux et un contrôle de sa fenêtre réelle. Le modèle existant acceptait déjà une seule caisse : seules la présentation des choix et la documentation ont été adaptées. Aucun changement de schéma, migration, service financier, permission serveur ou stockage sensible n’est introduit. Aucune donnée financière de développement n’a été modifiée.

Les nouveaux tests PostgreSQL exercent les encaissements CDF/USD, les soldes exacts, le refus de paiement sans approbation et d’auto-approbation, le paiement approuvé, ainsi que l’ouverture et la fermeture de session dans les deux configurations. L’ajout d’une deuxième caisse conserve exactement les opérations, écritures, reçus et compteurs existants ; ses nouveaux fonds commencent à zéro. Le périmètre d’un utilisateur restant affecté à une seule caisse ne s’élargit pas.

Les tests React couvrent le catalogue différé, la réapparition des sélecteurs sans perte de saisie, les anciennes caisses consultables et l’absence de réaffectation silencieuse lorsqu’une caisse devient indisponible. L’ajout d’une caisse reste accessible depuis une configuration unique. Les tests hybrides existants et le parcours navigateur hors connexion restent réussis ; les essais navigateur utilisent un double et ne prouvent pas une comptabilisation native réelle.

Commandes exécutées : `pnpm check`, `pnpm test:db`, `pnpm test:e2e`, `pnpm format:check`, puis compilation Tauri hors ligne avec les dépendances disponibles et `tests/native/smoke-linux.sh`. Les neuf migrations existantes sont rejouées uniquement sur une base de test temporaire supprimée ensuite. Les tests Rust de session, SQLCipher, API compilée en direct et le parcours intégré Rust/API n’ont pas été réexécutés pour cette adaptation de présentation ; leurs résultats précédents sont conservés dans l’historique ci-dessous.

La capture native vérifie l’ouverture et le rendu de la fenêtre de connexion, pas tous les parcours graphiques. La qualification Windows/macOS, les installateurs, les magasins de clés et l’impression physique restent à effectuer. La persistance sensible sur disque reste interdite et les brouillons restent temporaires en mémoire. Aucun écran de transfert n’étant exposé à l’étape 4, aucun bouton de transfert n’a été ajouté. Voir [configuration-caisses.md](configuration-caisses.md) pour la configuration et les responsabilités inchangées.

Les nouveaux tests PostgreSQL couvrent la création idempotente d’agence/caisse et les affectations, les droits de configuration, la séparation CDF/USD, le caractère non financier de la transmission, l’attestation obligatoire, six confirmations concurrentes et une reprise après reconnexion, les numéros uniques sur plusieurs encaissements concurrents, les montants exacts, le rollback après préparation des écritures, les justificatifs et leur cohérence SQL, l’immuabilité du reçu et du brouillon confirmé, les filtres, RLS, la révocation, l’ouverture concurrente d’une session de caisse, la consultation après désactivation, les versions de configuration et la concurrence entre modification et confirmation.

Le parcours intégré utilise la véritable API et la véritable bibliothèque Rust. Il configure une agence/caisse via un compte API restreint, transmet un brouillon sans modifier les fonds, le reprend dans un **nouveau courtier authentifié** avec le même UUID, confirme explicitement, réessaie la confirmation, puis vérifie le reçu, l’historique et les soldes `12.34 USD` / `0.00 CDF`. Le contrôle SQL final compte **1 opération, 2 écritures, 1 reçu et 1 brouillon**, sans doublon. Le test termine par les contrôles de verrouillage et de révocation. Base et rôle de test sont supprimés ensuite.

Les tests React vérifient aussi qu’une lecture de justificatif encore en cours est annulée au changement d’utilisateur, qu’aucun reçu n’est inventé après un résultat réseau inconnu et qu’un auditeur ne peut pas confirmer. Les tests navigateur examinent l’enchaînement visuel et le rendu imprimable avec un transport simulé ; ils ne sont pas comptés comme une confirmation financière réelle. Les captures/PDF de ce contrôle sont synthétiques et ignorés par Git.

Les essais ont corrigé un droit SQL d’exécution manquant pour la configuration et une mauvaise extraction de code d’erreur dans les messages enrichis de Prisma. Une migration supplémentaire ferme le cas SQL où un type de justificatif nul pourrait satisfaire un CHECK nullable ; le test direct du rôle de données vérifie le refus. L’idempotence comptable ne dépend plus de l’identifiant d’une session de connexion. Aucune erreur identifiée n’a été convertie en résultat positif et les assertions financières ont été conservées.

La persistance sensible reste **en mémoire uniquement**, avec expiration et isolation de session. Les installateurs, magasins de clés, impression physique et qualifications Windows/macOS restent reportés. Un reçu numéroté n’est pas présenté comme une signature numérique ou certification fiscale. Le guide [encaissements.md](encaissements.md) détaille les commandes, le workflow, les limites de fichiers et les actions manuelles.

Les tests HTTP/PostgreSQL vérifient les identifiants valides/invalides, la limitation des tentatives, les permissions insuffisantes, l’identité d’appareil, la déconnexion, le verrouillage, la rotation du jeton, l’expiration, la révocation du compte et des permissions, le renouvellement obligatoire du mot de passe, la préservation du dernier administrateur, les périmètres entreprise/agence/caisse et l’isolation des brouillons par auteur, y compris en RLS. Le provisionnement initial est exécuté dans le test, avec mot de passe synthétique sur stdin ; une seconde création est refusée.

Les tests Rust contrôlent l’absence de jeton/vérificateur dans les réponses au frontend, le refus de première connexion hors réseau, les permissions hors connexion, le déverrouillage local, le délai fixe non renouvelé par l’activité, le verrouillage et l’effacement, les montants exacts, les UUID/versions, les générations d’utilisateur et de rotation de jeton, la validation du serveur avant transmission du mot de passe et l’absence de synchronisation après révocation. Un profil serveur invalide entraîne l’effacement plutôt qu’une revalidation bloquée. Les caches ne sont pas vidés sur un simple réordonnancement des permissions ; une modification réelle de périmètre les invalide.

Le parcours intégré supplémentaire crée une base et un compte PostgreSQL temporaires. Le compte API ne peut pas lire directement les empreintes de mots de passe sans sélectionner son rôle autorisé. Le courtier Rust renouvelle les mots de passe initiaux, ouvre les deux sessions, teste un refus d’administration au caissier, lit les soldes exacts à zéro, envoie un brouillon une seule fois, verrouille/déverrouille puis vérifie le refus après changement de rôle. Le contrôle SQL final trouve **un brouillon, zéro opération financière et zéro écriture comptabilisée**. Les identifiants de test ne sont pas écrits en fichier ou affichés. La base et le rôle de test sont supprimés ensuite.

Les essais ont mis en évidence puis corrigé le chemin de chargement de la commande de provisionnement et un effet React StrictMode qui laissait le premier indicateur réseau en « Vérification… ». Un test et les deux essais navigateur protègent ce dernier cas. La disponibilité PostgreSQL sélectionne désormais explicitement le rôle restreint dans une transaction ; elle fonctionne aussi avec le LOGIN NOINHERIT du parcours intégré. Les tests nécessitant des sockets ont été relancés avec l’accès d’exécution adapté après un refus `EPERM` du bac à sable ; ce refus n’a pas été compté comme une réussite.

Le contrôle graphique prouve l’ouverture et le rendu du formulaire natif, pas le pilotage complet de tous les écrans. La connexion et la révocation réelles sont éprouvées par le parcours Rust/API distinct. La capture se trouve dans `native-test-results/caissepro-native.png`, ignorée par Git, et celle de l’aperçu navigateur dans `test-results/caissepro-login.png`. Aucun mécanisme de chiffrement local non qualifié, accès disque sensible ou reprise de session après redémarrage n’est activé. Voir [authentification.md](authentification.md) pour les actions manuelles et les conséquences d’une révocation inconnue hors connexion.

Commandes : `pnpm check`, `pnpm test:db`, `pnpm test:session`, `pnpm test:auth:desktop`, `pnpm test:local`, `pnpm test:api:live`, `pnpm test:e2e`, `pnpm format:check`, `pnpm db:validate`, `pnpm check:rust`, puis compilation `custom-protocol` et `pnpm test:native:linux`. Au 4 novembre, les étapes 1 et 2 n’étaient pas déclarées totalement qualifiées sans vérifications Windows/macOS et aucune étape suivante n’avait été commencée. L’étape 3 autorisée ensuite est décrite au début de ce rapport ; la qualification Windows/macOS reste reportée.

La dernière revue a reproduit puis corrigé deux défauts de cache : les dates limites non finies/fractionnaires et l’expiration antérieure à la date de synchronisation sont désormais refusées. Le démarrage API effectue une requête réelle au schéma PostgreSQL ; un simple `$connect()` de l’adaptateur à pool paresseux ne prouvait pas cette disponibilité. Un échec de démarrage ferme l’application et ses ressources. Les deux tests sur le binaire API vérifient ces comportements.

Le contrôle natif initial vérifiait la présence d’une fenêtre ; sa première capture montrait une image blanche. Le contrôle attend désormais un rendu non vide, avec délai borné, et fait échouer une capture blanche. La capture finale a été inspectée : accueil CaissePro, navigation, devises séparées et état hors connexion apparaissent réellement dans WebKitGTK. Aucun réglage désactivant le bac à sable WebKit n’a été ajouté. Les avertissements AT-SPI du conteneur proviennent de son bus d’accessibilité absent ; ils n’ont pas empêché le rendu. Ce contrôle ne constitue pas une validation de tous les parcours natifs.

La précision intermédiaire des conversions a été portée à 60 chiffres après constat d’un écart d’un centime sur un grand montant. Un test PostgreSQL supplémentaire vérifie la valeur exacte et la validation au commit.

Les tests PostgreSQL couvrent l’exactitude décimale et les grands montants, la séparation des devises, six requêtes concurrentes avec une même clé d’idempotence, les doubles transferts concurrents, les réservations concurrentes, l’auto-approbation interdite également en SQL, le paiement idempotent après approbation, le rollback, l’immuabilité et le scellement des écritures, les contre-écritures, les conversions, les permissions et révocations, RLS, les sessions fermées, les justificatifs et la synchronisation des seules données de brouillon sans mouvement financier.

Les tests SQLCipher portent sur des données synthétiques : fichier réellement chiffré, refus d’une clé erronée et d’une lecture SQLite sans clé, contrôle de périmètre, migrations répétables, décimaux stockés en texte, concurrence de deux connexions, expiration et permissions du cache, métadonnées sans confirmation financière, corruption détectée et effacement fichier/clé. Les messages HMAC attendus des tests négatifs ne contiennent pas les données de test ni les clés. Aucun test de magasin natif Windows/macOS n’est compté dans les neuf tests Linux.

Un premier téléchargement Chromium a été refusé par la politique réseau ; les tests ont utilisé `/usr/bin/chromium` déjà installé. Les contrôles ne désactivent ni TLS ni les sommes de contrôle. Une relance des tests simultanément à la compilation native a rencontré des délais dépassés ; les scripts exécutent désormais les suites successivement pour limiter la charge. Les erreurs n’ont pas été transformées en succès et les assertions financières n’ont pas été retirées.

Les versions verrouillées du stockage sont `rusqlite 0.41.1`, SQLCipher 4.19.0 (SQLite 3.53.4), OpenSSL 3.6.3 ; les `Cargo.lock` restent la référence. Tauri est verrouillé à 2.12.5 et son outil de build à 2.7.4. Les avertissements Rollup relatifs aux commentaires d’annotation de Zod n’empêchent pas le build ; ils ne sont pas présentés comme des erreurs applicatives.

Dans cet état historique du 4 novembre, l’authentification, le transport authentifié et les événements de révocation n’étaient pas livrés ; ils sont désormais décrits dans la section étape 3. Les installateurs signés Windows/macOS et l’activation du disque sensible restent non qualifiés. La porte de stockage reste fermée. Une CI de bibliothèque réussie devra encore être complétée par la qualification des applications distribuées et de leurs magasins de clés. La consultation non authentifiée de la page GitHub Actions a répondu HTTP 404 ; aucun résultat distant Windows/macOS n’est déduit de ce refus d’accès.
