# Validation de CaissePro — 9 novembre 2026

## Préparation de la démonstration sur Mac

Ajout d'un guide français et du lanceur `bash scripts/demo-macos.command`, avec contrôle préalable `--check`, refus d'un Docker distant et d'une configuration PostgreSQL différente de la base locale attendue, verrou de lancement et arrêt des seuls processus démarrés. Les mots de passe restent générés localement hors Git. Aucun installateur ni serveur public n'est publié.

Validation dans le cloud Linux : syntaxe Bash, ESLint, Prettier et **6 nouveaux tests Node réussis**, plus le contrôle existant des permissions Tauri. Les tests vérifient notamment les connexions refusées, l'absence de préparation avec `--check`, les paramètres publics de l'application, la conservation du fichier d'état et l'arrêt du serveur simulé après réussite ou échec du desktop. Les commandes Mac sont remplacées par des doubles et une API HTTP fictive ; **aucune compilation, ouverture de fenêtre ou impression macOS réelle n'est attestée** par ces tests.

### Coexistence avec une autre base PostgreSQL locale

Le lanceur accepte désormais `--db-port=5433` pour une première préparation. Le port est conservé dans `.env`, avec connexion PostgreSQL et publication Docker cohérentes sur loopback. Les mots de passe et autres paramètres sont préservés. Une démo déjà préparée sur un autre port est refusée avant modification, pour éviter un déplacement implicite de données.

**9 contrôles Node réussis** (8 du lanceur et 1 des permissions Tauri), ESLint et formatage réussis. Un test Docker/PostgreSQL réel a démarré un projet temporaire sur `127.0.0.1:5433`, vérifié la connexion SQL et constaté que tous les conteneurs préexistants restaient actifs. Seuls le projet et le volume temporaires du test ont ensuite été retirés. La configuration et les données du projet existant n'ont pas été modifiées par cette vérification. Ce test Linux ne qualifie pas l'application native macOS.

### Personnalisation du mot de passe de démonstration

`pnpm demo:password` permet de remplacer le mot de passe du seul compte `admin@demo.caissepro.test` depuis une autre fenêtre de Terminal, pendant que l'API de démonstration tourne. La saisie est masquée et confirmée, avec 12 à 128 caractères. Le mot de passe initial est lu dans le fichier privé pour éviter sa recopie. Le nouveau n'est pas enregistré sur disque. Le fichier d'accès est seulement annoté pour signaler que le mot de passe commun ne convient plus à l'administrateur.

Validation : **5 nouveaux tests Node réussis**, en complément des 9 contrôles du lanceur et des permissions. Ils vérifient l'identité du serveur et du compte, l'identifiant d'appareil requis, les saisies refusées avant authentification, l'absence de secret nouveau dans les fichiers et l'absence de rejeu en cas de réponse incertaine. ESLint, syntaxe et formatage ciblés réussis.

Un parcours supplémentaire sur **API et PostgreSQL réels**, dans une base temporaire et avec un LOGIN restreint NOINHERIT/NOBYPASSRLS, a confirmé le nouveau mot de passe, le refus de l'ancien, la révocation d'une session antérieure, l'événement `PASSWORD_CHANGED` et l'absence d'opération financière. La base, le rôle et les fichiers temporaires ont été supprimés après le contrôle. Les accès de la démonstration existante sont préservés. La saisie interactive macOS reste à vérifier sur le poste utilisateur.

Les tests PostgreSQL couvrent l’exactitude décimale et les grands montants, la séparation des devises, six requêtes concurrentes avec une même clé d’idempotence, les doubles transferts concurrents, les réservations concurrentes, l’auto-approbation interdite également en SQL, le paiement idempotent après approbation, le rollback, l’immuabilité et le scellement des écritures, les contre-écritures, les conversions, les permissions et révocations, RLS, les sessions fermées, les justificatifs et la synchronisation des seules données de brouillon sans mouvement financier.

Les tests SQLCipher portent sur des données synthétiques : fichier réellement chiffré, refus d’une clé erronée et d’une lecture SQLite sans clé, contrôle de périmètre, migrations répétables, décimaux stockés en texte, concurrence de deux connexions, expiration et permissions du cache, métadonnées sans confirmation financière, corruption détectée et effacement fichier/clé. Les messages HMAC attendus des tests négatifs ne contiennent pas les données de test ni les clés. Aucun test de magasin natif Windows/macOS n’est compté dans les neuf tests Linux.

Un premier téléchargement Chromium a été refusé par la politique réseau ; les tests ont utilisé `/usr/bin/chromium` déjà installé. Les contrôles ne désactivent ni TLS ni les sommes de contrôle. Une relance des tests simultanément à la compilation native a rencontré des délais dépassés ; les scripts exécutent désormais les suites successivement pour limiter la charge. Les erreurs n’ont pas été transformées en succès et les assertions financières n’ont pas été retirées.

Les versions verrouillées du stockage sont `rusqlite 0.41.1`, SQLCipher 4.19.0 (SQLite 3.53.4), OpenSSL 3.6.3 ; les `Cargo.lock` restent la référence. Tauri est verrouillé à 2.12.5 et son outil de build à 2.7.4. Les avertissements Rollup relatifs aux commentaires d’annotation de Zod n’empêchent pas le build ; ils ne sont pas présentés comme des erreurs applicatives.

Dans cet état historique du 4 novembre, l’authentification, le transport authentifié et les événements de révocation n’étaient pas livrés ; ils sont désormais décrits dans la section étape 3. Les installateurs signés Windows/macOS et l’activation du disque sensible restent non qualifiés. La porte de stockage reste fermée.
